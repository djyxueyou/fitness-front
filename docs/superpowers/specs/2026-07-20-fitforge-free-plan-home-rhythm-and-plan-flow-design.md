# FitForge 免费计划额度、首页本周节奏与计划流程修正设计

日期：2026-07-20

状态：已于 2026-07-20 经用户确认，进入实施计划

范围：`fitness-front`、`fitness-server`、数据库 schema 与迁移 SQL、根目录产品文档

当前有效规则：

- 首页“本周节奏”是免费基础反馈；周统计详情、历史周趋势、周报和高级分析属于 Pro。
- 免费用户可拥有 1 个有效“我的计划”，Pro 数量不限。
- 系统计划执行不占额度，保存为独立副本后才占额度。
- 计划额度由 MySQL 事务、用户行锁和索引计数保证，不使用 Redis 计数。
- 当前安排支持停用；首页选择计划根据“我的计划”数量进入系统或我的子页。

## 1. 文档地位

本文是对 `2026-07-19-fitforge-product-scope-membership-level-redesign.md` 的增补和局部修订。两者冲突时，以本文为准。

本文明确修订以下旧结论：

- 首页“本周节奏”不再属于 Pro，登录用户均可查看当前自然周的场次、容量、时长和 7 日训练分布。
- 免费用户不再被完全禁止使用自定义训练计划，而是最多拥有 1 个有效“我的计划”；Pro 数量不限。
- 系统计划执行本身不占“我的计划”额度，只有保存为“我的计划”的独立副本才计入额度。

以下已确认规则不变：

- 动作收藏属于 Pro。
- 周统计详情、周报、历史周趋势和高级分析属于 Pro。
- 免费用户最多拥有 1 个自定义动作和 1 个自定义训练模板。
- 不提供新用户自动会员试用。
- 不做产品事件漏斗、计划/周报公开分享、归因二维码和连续训练等级规则。

## 2. 背景与问题

本轮需要修复六类已确认问题：

1. 首页“本周节奏”被错误地整体放入会员能力。
2. 免费用户创建第一个自定义训练计划也会失败，且前端只提示“创建计划失败”，没有表达真实原因。
3. 浅色主题下重命名“我的模板”时，输入框文字与背景对比不足。
4. 新建模板返回列表后仍显示空列表，写后缓存没有失效。
5. 当前系统计划可以保存为“我的计划”，但没有统一免费额度；当前安排页也缺少停用入口。
6. 首页无当前计划时进入计划中心，可能停留在此前的空“我的计划”子页，和“选择训练计划”的意图不一致。

本轮目标不是只修页面表现，而是建立统一、不可绕过的后端业务规则，并减少首页与额度判断的无效查询。

## 3. 产品与技术原则

1. **后端统一裁决**：会员状态、免费额度、计划来源、可编辑性、保存幂等和当前计划状态都以后端为准。
2. **前端不预判授权结果**：前端可以展示额度说明，但不得用本地数量作为最终授权依据。
3. **所有创建入口同规则**：手动创建、复制已有计划、把系统计划执行保存为“我的计划”共用同一额度规则。
4. **并发不可突破额度**：同一免费用户同时发起多个创建请求，最终最多只能新增 1 个有效“我的计划”。
5. **用户资产不丢失**：会员到期或额度降低不删除计划；查看和删除始终可用。
6. **低频写保证一致性，高频读优先聚合**：计划额度使用事务和索引计数；首页使用专用聚合接口，不加载不需要的历史明细。
7. **不引入双写计数**：当前阶段不增加 Redis 额度计数器或用户计划数量冗余字段，避免缓存失效和数据修复成本。

Redis 决策补充：项目虽然已经包含 Spring Data Redis 依赖和连接配置，但当前没有使用 Redis 承担业务额度事实。计划额度继续由 MySQL 事务保证；Redis 以后可以用于会员状态短缓存、限流或高频统计缓存，但不得作为“我的计划”数量的唯一事实来源。

## 4. 最终权益与计数口径

| 能力 | 免费用户 | Pro 用户 |
| --- | --- | --- |
| 首页当前周“本周节奏” | 可查看 | 可查看 |
| 周统计详情、周报和历史周趋势 | 不可查看 | 可查看 |
| 系统计划浏览、调整、启用、停用 | 可使用 | 可使用 |
| 当前系统计划执行 | 不计“我的计划”额度 | 不计额度 |
| 有效“我的计划” | 最多 1 个 | 不限 |
| 创建、复制或保存新的“我的计划” | 未达到 1 个时可用 | 可用 |
| 编辑“我的计划” | 当前有效数量不超过 1 个时可用 | 可用 |
| 查看、停用、删除计划 | 可用 | 可用 |

“有效我的计划”的唯一计数条件为：

```text
user_training_plan_definition.user_id = 当前用户
AND is_saved = 1
AND status = 'ACTIVE'
```

以下内容不计入额度：

- `is_saved = 0` 的系统计划运行时定义。
- `status = 'ARCHIVED'` 的已删除计划。
- 用户历史上创建过、但已经归档的计划次数。

来源 `USER`、`SYSTEM_COPY` 等只用于说明计划来源，不改变计数口径。只要计划同时满足“当前用户、已保存、有效”，就占用 1 个额度。

### 4.1 免费与到期后的编辑规则

- 免费用户当前有效计划数为 0 或 1 时，可以编辑已有的唯一计划。
- 因会员到期、退款或开发数据导致当前有效计划数超过 1 时，计划继续可查看、可启用、可停用、可删除，但不能新增、复制或编辑。
- 用户删除到只剩 1 个后，恢复剩余计划的编辑权限；删除到 0 个后，可以重新创建。
- 删除操作不检查会员和额度，避免用户无法自行回到免费额度内。

## 5. 后端架构

### 5.1 计划额度服务边界

在计划模块建立单一额度裁决单元 `UserPlanQuotaService`。它只负责以下问题：

- 当前用户是否为有效 Pro。
- 免费用户是否还能新增有效“我的计划”。
- 免费用户是否还能编辑已有计划。
- 在需要新增时，对同一用户的并发写进行串行化。

`UserPlanService` 仍负责计划定义、训练日、模板快照和执行关系；不得在 Controller 或前端重复实现额度逻辑。

新增计划的事务顺序：

```text
进入 @Transactional Service
  -> 查询会员状态
  -> Pro：直接进入创建，不查询免费额度
  -> 免费：SELECT user ... FOR UPDATE 锁定当前用户行
  -> 使用 COUNT(*) 查询有效“我的计划”数量
  -> 数量 >= 1：抛出 40311
  -> 数量 < 1：在同一事务中创建完整计划
  -> 提交事务并释放用户行锁
```

统一错误：

```text
code: 40311
message: 免费版最多可拥有 1 个我的计划，删除已有计划或开通 Pro 后可继续。
```

规则补充：

- 会员查询异常时写操作失败并提示稍后重试，不得为了可用性放开额度。
- 用户行不存在时按无效登录用户处理，不继续创建。
- 额度判断只在一次顶层创建事务中执行，不在复制每个训练日或动作项时重复查询会员和额度。
- `create`、`copy`、`saveExecutionAsMyPlan` 必须使用同一新增额度方法。
- `update`、`createDay`、`updateDay`、`deleteDay` 使用同一编辑权限方法。
- `delete`、`activate`、`stopActive` 不检查会员。

### 5.2 性能与并发选择

计划创建属于低频写操作，使用数据库行锁比维护 Redis 或冗余计数更简单可靠。

性能约束：

- Pro 的手动创建和普通复制路径只做已有的会员状态点查，不执行免费额度 `COUNT(*)`，也不获取用户行锁；“存为我的计划”为保证写幂等，免费和 Pro 都获取用户行锁。
- 免费创建路径只增加一次用户行锁和一次索引计数。
- 计数 SQL 使用精确等值条件 `user_id + is_saved + status`，复用 `idx_user_plan_definition_saved`，不得加载计划列表后在 Java 中计数。
- 不为每个计划训练日重复执行权限查询。
- 同一用户的免费创建会串行，不同用户之间不互相阻塞。
- 计划复制保持单事务；本轮不为低频、有限规模的计划复制引入异步任务或队列。

### 5.3 系统计划“存为我的计划”幂等

在 `user_training_plan_definition` 增加：

```text
saved_from_execution_id BIGINT NULL
```

并增加唯一索引：

```text
UNIQUE KEY uk_user_plan_saved_execution (user_id, saved_from_execution_id)
```

MySQL 允许唯一索引中存在多条 `NULL`，因此手动创建和普通复制不受影响。

保存规则：

1. 后端验证 execution 属于当前用户。
2. 后端验证该 execution 来自仍未保存的系统计划定义；用户计划执行不能调用该接口再次复制。
3. 对当前用户加行锁，按 `(user_id, saved_from_execution_id)` 查询已有有效副本。
4. 已存在时直接返回已有副本，不再次克隆训练日和模板。
5. 不存在时执行会员/免费额度判断，再创建独立副本。
6. 归档该副本时将 `saved_from_execution_id` 置为 `NULL`；用户之后可以从仍在执行的系统计划重新保存一个新副本。

无论免费还是 Pro，“存为我的计划”都进行同一用户级串行化，因为该接口还承担写幂等，且属于低频操作。

当前安排响应增加：

```text
savedDefinitionId: Long | null
```

后端通过唯一索引点查当前 execution 是否已有有效副本。前端刷新页面后仍能显示“已保存”，不能只依赖页面内存变量。

### 5.4 数据库变更

新增增量 SQL，并同步 `schema.sql`：

- `user_training_plan_definition.saved_from_execution_id`。
- 唯一索引 `uk_user_plan_saved_execution (user_id, saved_from_execution_id)`。
- 训练记录复合索引 `idx_training_record_user_started (user_id, started_at)`。

已有 `idx_user_plan_definition_saved (user_id, is_saved, status, updated_at)` 足以支持免费额度计数，不新增重复索引。

产品尚未上线，不为旧版本保留双读、双写或兼容字段。现有开发数据中的历史 `SYSTEM_COPY` 不强行反推 execution 来源。

## 6. 首页“本周节奏”

### 6.1 产品边界

首页“本周节奏”是训练后的基础即时反馈，不是完整分析报告。登录用户均可查看：

- 当前自然周训练场次。
- 当前自然周总容量。
- 当前自然周训练时长。
- 周一至周日是否有训练记录。

以下内容继续属于 Pro：

- 任意历史周或自定义时间范围统计。
- 与上周对比、趋势变化、肌群分布、PR 趋势。
- 周报结论、风险提示、恢复分析和下周建议。
- “训练分析”页面及其深度详情。

首页标题文案从“保持连续，比一次练满更重要”调整为“查看本周完成情况”，避免重新引入已取消的连续训练达标概念。

### 6.2 专用后端接口

新增：

```http
GET /api/trainings/home/weekly-rhythm
```

接口需要登录，不检查会员，不接收客户端日期参数。自然周范围由后端 `BusinessClock` 统一计算为周一 00:00 至下周一 00:00，避免客户端时区和日期篡改导致多端不一致。

响应：

```json
{
  "weekStart": "2026-07-20",
  "weekEnd": "2026-07-26",
  "sessionCount": 2,
  "totalVolumeKg": 3200.00,
  "totalDurationSeconds": 5400,
  "trainedDates": ["2026-07-20", "2026-07-23"]
}
```

Mapper 使用一次聚合查询返回一行：

- `COUNT(*)` 计算场次。
- `COALESCE(SUM(total_volume_kg), 0)` 计算容量。
- `COALESCE(SUM(duration_seconds), 0)` 计算时长。
- `GROUP_CONCAT(DISTINCT DATE(started_at) ORDER BY DATE(started_at))` 生成最多 7 个训练日期。

查询条件使用半开区间：

```text
user_id = ? AND started_at >= ? AND started_at < ?
```

并使用 `idx_training_record_user_started (user_id, started_at)`。当前周最多返回 7 个去重日期，不受 `GROUP_CONCAT` 长度限制影响。

### 6.3 前端数据流

首页登录后并行请求当前计划、最近记录和 `weekly-rhythm`。本周节奏不再依赖会员状态，也不再请求：

- 带日期范围的 `/api/trainings/stats/summary`。
- 为计算 7 日分布而加载最多 50 条本周训练历史。

这会把本周节奏从两个 HTTP 请求和最多 50 条明细传输，收敛为一个固定结构的聚合请求。

首页继续使用 30 秒短缓存；训练保存、修改或删除事件发生后立即使本周节奏缓存失效。接口失败时只把本周节奏显示为暂不可用，不阻断今日训练、计划和最近记录。

## 7. 模板重命名与写后刷新

### 7.1 重命名可读性

`template-manager__input` 必须使用主题语义变量：

- 文字：`var(--app-text)`。
- 背景：`var(--app-surface-subtle)` 或 `var(--app-surface)`。
- 边框：`var(--app-border-strong)`。
- 聚焦边框：`var(--app-accent)`。

输入框增加合理左右内边距，名称最长 30 个字符；空名称、保存中状态不允许重复提交。浅色和暗色主题都必须达到清晰可读。

### 7.2 模板创建后的列表一致性

当前问题由 30 秒列表缓存导致：编辑页直接调用创建 API 后再调用未带 `force` 的 `fetchTemplates()`，缓存仍有效时请求会被跳过。

修正原则：

- 模板创建和更新统一通过 Template Store 的写方法，不由页面直接调用 API。
- Store 使用后端写接口返回的完整模板结果立即更新 `items` 与 `detailCache`，保证返回列表时新模板已存在。
- 写接口返回值足够更新本地列表时，不额外请求全部模板详情。
- 仅在返回值不足、写后同步失败或明确标记 dirty 时，管理页 `onShow` 执行一次轻量列表强制刷新。
- 新建模板默认排在“我的模板”顶部。
- 写失败时保留编辑内容，并展示后端真实错误；不得先返回列表再静默丢失结果。

## 8. 当前计划管理

### 8.1 “存为我的计划”交互

- 免费用户当前有效“我的计划”为 0：按钮可用，保存后占用唯一免费额度。
- 免费用户已经有 1 个：按钮仍可点击，由后端返回 40311；前端展示额度说明，并提供“管理我的计划”和“查看 Pro”操作。
- Pro：按钮可用且数量不限。
- 已经从该 execution 保存过：按钮显示“已保存”，刷新页面后状态不丢失。
- 当前系统计划不需要先保存才能继续执行；保存只代表生成可独立编辑的副本。

前端不得仅依据本地列表数量禁用接口，也不得把所有错误统一显示为“保存到我的计划失败”。

### 8.2 停用当前计划

后端已有 `POST /api/plan-executions/active/deactivate`，停用属于免费核心能力。本轮在“当前安排”页增加“管理计划”入口，并使用统一 `AppActionSheet` 展示：

- 停用当前计划。
- 当系统计划尚未保存时，保留“存为我的计划”作为独立操作。

确认文案：

```text
停用后首页不再展示该计划的训练安排，已完成的训练记录和进度历史会保留。
```

停用成功后：

- 后端把 active execution 标记为 `STOPPED` 并记录 `ended_at`。
- 前端清理当前计划摘要、当前执行和今日计划建议缓存。
- 返回计划中心，并明确进入系统计划子页。
- 首页恢复“选择训练计划”状态。

停用接口保持幂等：没有当前计划时仍返回成功，不制造无意义错误。

## 9. 首页到计划中心的导航意图

`switchTab` 不能可靠携带查询参数，计划页又会保留上次子页状态，因此通过 `TrainingHubStore` 增加一次性计划子页意图：

```text
requestedPlanTab: 'system' | 'mine' | null
requestPlanTab(tab)
consumeRequestedPlanTab()
```

导航规则：

- 首页无当前计划且“我的计划”为 0：进入计划中心的“系统计划”。
- 首页无当前计划但已有可用“我的计划”：进入“我的计划”，引导启用已有计划。
- 计划页底部 Tab 的普通直接进入：保留用户上次选择的系统/我的子页。
- “我的计划”空态提供主按钮“浏览系统计划”，点击后切到系统计划。
- 停用当前计划后：进入系统计划子页，方便重新选择。

计划中心在 `onShow` 时只消费一次显式意图，消费后清空，避免影响后续用户自主切换。

## 10. 前端错误处理

所有计划写操作遵循以下顺序：

1. 仅做登录校验，不在前端提前阻断免费用户的第一个计划。
2. 调用后端接口。
3. `ApiError.code === 40311` 时展示后端额度文案和会员入口。
4. 参数错误展示后端可读业务文案。
5. 网络异常显示“网络异常，请稍后重试”。
6. 未知异常显示具体动作的通用错误，如“计划创建失败，请重试”。

`membership-guard` 中的免费额度能力包含：

- 自定义动作。
- 自定义训练模板。
- 自定义训练计划。

这些能力通过前端登录校验后直接请求后端，由后端决定是允许免费额度还是返回 40311。

## 11. 接口与数据契约变化

新增接口：

- `GET /api/trainings/home/weekly-rhythm`。

修改接口：

- `GET /api/plan-executions/active` 增加 `savedDefinitionId`。
- `POST /api/plan-executions/{executionId}/save-as-my-plan` 增加免费额度、来源验证和幂等规则，路径与成功响应结构不变。
- `POST /api/user-plans`、`POST /api/user-plans/{id}/copy` 改为“免费 1 个、Pro 不限”。
- `PUT/POST/DELETE` 用户计划及训练日写接口按本文的编辑和删除规则执行。

保留接口：

- `/api/trainings/stats/summary` 的任意日期范围统计继续要求 Pro。
- `/api/trainings/analytics/**` 和周报接口继续要求 Pro。
- `/api/plan-executions/active/deactivate` 保持免费、幂等。

## 12. 测试与验收

### 12.1 后端业务测试

- 免费用户无有效“我的计划”时，手动创建成功。
- 免费用户已有 1 个时，手动创建、复制和保存系统执行均返回 40311 及统一文案。
- Pro 用户创建、复制和保存数量不限。
- 免费用户可以编辑唯一计划；超额免费用户不能编辑，但可以查看、启用、停用和删除。
- 删除后额度立即释放。
- 两个并发免费创建请求最终最多新增 1 个有效计划。
- 同一 execution 重复或并发保存只生成 1 个有效副本，并返回同一 `savedDefinitionId`。
- 用户不能保存他人的 execution，也不能通过保存接口复制用户计划 execution。
- 停用当前计划幂等，历史训练记录和执行日完成事实不删除。
- 首页本周节奏接口不检查会员，只统计后端自然周，跨周边界正确。
- 首页聚合无记录时返回 0、0、0 和空日期数组，不返回 `null`。

### 12.2 数据库与性能验收

- schema smoke test 验证新增字段和索引存在。
- `EXPLAIN` 能使用 `idx_training_record_user_started` 处理当前周范围聚合。
- 免费额度计数使用 `idx_user_plan_definition_saved`，不加载计划详情或训练日。
- 首页只发送一个本周节奏请求，不再为 7 日分布请求本周训练明细。
- Pro 创建不执行免费额度计数和用户行锁。
- 计划复制只在顶层执行一次会员/额度判断。

### 12.3 前端验收

- 免费用户首页直接看到本周场次、容量、时长和 7 日分布，不出现 Pro 锁卡。
- “训练分析”入口仍向免费用户展示 Pro 权益，不泄露分析结果。
- 免费用户能创建并编辑第一个“我的计划”，第二个创建展示准确额度提示。
- 创建模板后返回管理页，新模板立即出现在顶部。
- 浅色与暗色主题下重命名输入均清晰可读。
- 当前系统计划可停用；停用后首页和计划中心状态立即刷新。
- 系统计划已保存时，刷新当前安排页仍显示“已保存”。
- 首页无计划且无“我的计划”时，点击“选择训练计划”进入系统计划，不再落到空列表。
- “我的计划”空态可以一键进入系统计划。
